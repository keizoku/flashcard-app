# 設計書

フラッシュカードアプリ（YouTube の字幕から英文の暗記カードを作るアプリ）の設計書です。
使い方は [../README.md](../README.md) を見てください。ここでは「どう作られているか」「なぜそうしたか」を書きます。

| 文書 | 内容 |
| --- | --- |
| [setup.md](setup.md) | セットアップの説明書（Windows・Mac・Linux） |
| [architecture.md](architecture.md) | 全体の構成、ディレクトリ、処理の流れ、外部とのつながり |
| [data-model.md](data-model.md) | テーブル同士の関係（図）、マイグレーションの履歴 |
| [tables.md](tables.md) | テーブル定義書（全テーブルの全列、キー、インデックス） |
| [features.md](features.md) | 機能ごとの設計（字幕の解析、カード、記憶テスト、物語、統計など） |
| [auth.md](auth.md) | ユーザー登録・ログイン・セッション・データの分離、セキュリティ上の決まり |
| [test-spec.md](test-spec.md) | テスト仕様書（条件と期待する結果の表、網羅の状況） |
| [testing.md](testing.md) | 単体テストの方針、実行方法、機能とテストの対応 |

## メンテナンスの決まり

- **コードを変えたら、同じコミットで設計書とテストも直す。** 設計書とコードが食い違ったら、コードが正しいとは限らないので、どちらが意図どおりかを確かめてから合わせる
- 新しい機能・画面・テーブルを足したら、該当する文書に節を足し、[testing.md](testing.md) の対応表にテストを書き足す
- テストを足したら、名前の先頭に ID（`ST-11` など）を付け、[test-spec.md](test-spec.md) に条件と期待する結果の行を足す
- テーブルを変えたら [tables.md](tables.md) の定義と [data-model.md](data-model.md) の図・履歴を直す（`db/migrations/` に足したファイル名も書く）。
  tables.md と DB が食い違うと、単体テスト（`test/db/schema-doc.test.js`）が失敗する
- 数字（間隔の日数、文字数の上限など）は、コードの定数名も添えて書く（あとで探しやすくするため）
- コミットの前にテストが自動で走る（[testing.md](testing.md)）。Markdown だけの変更なら走らない（テスト仕様書・テーブル定義書を変えたときは走る）
