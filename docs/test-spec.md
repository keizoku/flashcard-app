# テスト仕様書

単体テストが「どんな条件で」「何を期待して」確かめているかを、機能ごとの表（マトリックス）で書く。
テストの動かし方やしくみは [testing.md](testing.md) にある。

## 見方

- 1行が1つの条件。「テスト」の列は、それを確かめているテストの ID
- ID はテストの名前の先頭に付いている（例: `test("ST-03 覚えていると…")`）。
  `docker compose exec app npm test` の結果や、テストのファイルを ID で検索すると見つかる
- 「テスト」の列が **未** の行は、まだテストがない条件（網羅できていないところ）
- ブラウザで1件ずつ実行するときは、テスト実行ツール（`docker compose exec app npm run test:ui` → http://localhost:3100）を使う
- 1つのテストが、いくつもの条件をまとめて確かめていることがある（同じ ID が何行かに出る）

## この仕様書のメンテナンス

- テストを足したら、この表に行を足して ID を書く。ID は「接頭辞-次の番号」（使った番号は使い回さない）
- テストのない条件に気づいたら、**未** の行として足しておく。テストを書いたら ID に書き換える
- 作っていない機能は、ここには書かない（[features.md](features.md) に書く）
- 網羅の状況の表は、`docker compose exec app node test/specDoc.mjs` で作り直せる
- 次のことは、単体テスト（DOC-03、DOC-04）が確かめる。食い違うとテストが失敗する
  - テストのファイルにある ID が、すべてこの仕様書にある（書き忘れがない）
  - この仕様書に書いた ID が、すべてテストのファイルにある（消したテストが残っていない）
  - 下の「網羅の状況」の数が、各節の行の数と合っている
